01

Product Scope

一个面向英语学习者的 Web 应用。核心叙事是把用户记错的单词沉淀成私有数据，再用 AI 围绕这些错词生成练习、批改作文，宣称形成"错词 → 出题 → 写作 → 批改 → 回流"的学习闭环（实际数据流见下面图 4，这个闭环在代码里并没有闭上）。围绕主线还实现了额度体系、付费套餐、反馈、公告与完整管理后台。

先看红色虚线的四格。它们是这个产品自己口号里承诺、但代码里没有的东西：错词没有自动入库的入口、批改和出题发现的错误不回流、错词也没有"掌握后移出"的概念。错词本因此只是一个手动维护的词表，所以降为"残缺"。这四格是全图最要紧的部分，下面的"产品逻辑"会展开。
再看灰色虚线。"说"这一行完全没有，而口语对话和发音评测正是现在 AI 英语产品竞争最激烈的地方；"词"缺背单词的记忆算法（遗忘曲线、间隔重复这类）；"激励"几乎是零，没有排行、分享、社区。做得最扎实的是"写"这一行，比大多数同类产品都密。

终点

不写回错词本

缺失的边：批改 → 错词本（无）· 出题答错 → 错词本（无）· 听写答错 → 错词本（无）· 错词本 → 写作（无）· 掌握后移出错词本（没有这个概念）

看图就清楚了：代码里没有一条"回流"的边。错词本的唯一来源是用户手打；出题和听写只从它读，答错了不写回去；批改是整个系统里唯一真正能发现用户错误的地方，可它的结果只进写作历史，不进错词本，而且写作也不从错词本取词。所谓闭环，其实是两条互不相连的直线："手打错词 → 出题/听写 → 记录（还坏了）"，和"自由写作 → 批改 → 历史"。

还少一个概念：没有"掌握"。错词本只增不减，一个词进来就永远在里面，答对多少次都不会移出。百词斩、扇贝的错词本是"测出来的，复习到会了就走"；这里是"自己填进去的，永远留着"。严格说它现在不是错词本，是一个用户手动维护的词表。这也是 §07 里"没人会用"最根本的原因：不是录入麻烦，是系统没有替用户产生错词的环节，起点是空的。

详细发现

Detailed Findings

严重 · Critical（6）

严重C-1数据 / 出题
整个「练习历史」永远为空：数据库里没有这张表
现象完整做完一整套阅读理解并提交后，练习历史仍显示"还没有练习记录"。
证据
POST /api/exercises/submit → 500
Supabase POST ExerciseRecord 404: {"code":"PGRST205",
 "message":"Could not find the table 'public.ExerciseRecord'"}
影响后端往不存在的表写入；前端 catch(e){console.error(...)} 把错误吞掉，界面照常显示，缺陷可长期无人察觉。
建议在 Supabase 建 ExerciseRecord 表；两处 catch 改为 showToast('保存失败','error')，静默吞异常是它藏这么久的根因。
严重C-2前端 / 接口
仪表盘整块「额度」卡片永不显示：URL 多写一个 /api
证据
API_BASE = '...onrender.com/api'   // 第 1454 行
fetch(`${API_BASE}/api/user/usage`) → /api/api/... → 404
手动请求正确地址 /api/user/usage → 200（后端正常）
影响userUsage 恒为 null，源码 156–195 行整块额度卡片一次都没渲染过；用户不知剩余次数，只能被"额度已用完"弹窗拦住。
建议删除三处多余 /api（第 2196 / 2212 / 2237 行）。三行改动换回整块 UI 与全部付费接口，全篇性价比最高。
严重C-3逻辑 / 听写
听写判分用子串匹配：输入一个「的」字可得 80 分
证据
isCorrect = userAnswer === meaning || meaning.includes(userAnswer);
// 全部 5 题只输入 "的" → 得分 80，答对 4/5
影响任意子串即判对，释义几乎必含"的/，/adj"。功能完全失去检测能力。
建议止血：答案 ≥ 2 字且命中某一分号切分义项。根治：en2zh 交给已在用的大模型判语义等价，零成本复用现有 AI 能力。
严重C-4数据 / 听写
听写成绩不落库：刷新即丢，也不进统计
现象submitDictationAnswer() 全程无任何网络请求（抓包确认零后端调用）。得分只在内存，刷新即失。
影响结合 C-3，听写页现状是：判分错误 + 成绩不保存。
建议听写结束复用 /exercises/submit（type:'dictation'），与阅读/完型同链路；前提是先建 C-1 的表。
严重C-5安全 / 账号
注册接口零校验：假邮箱、1 位密码可注册，无邮箱验证
证据
密码 "1"        → 200 发 token   无密码长度校验
邮箱 "notanemail" → 200 发 token   无邮箱格式校验
空字段          → 400「均为必填」    仅"非空"这一层
影响假邮箱可建号（注册即登录，无激活）；弱密码可爆破；可被脚本批量注册，C-6 烧钱链的第一环。
建议服务端校验邮箱格式 + 密码 ≥ 8 位；接入邮箱验证码/激活，注册后置为未激活。
严重C-6安全 / 成本
AI 批改接口无输入长度上限：会直接烧毁模型账单
证据
向 /api/writings/grade 发 200KB 请求体
bytes = 200000　status = 200　耗时 5416ms（模型真被调用）
影响无长度校验、无 413。配合免费注册（C-5），可批量注册 + 每次塞 200KB，低成本打爆账单。唯一一条会真正亏钱的问题。
建议调模型前卡死 content.length（5000 字符封顶）返回 400；Express 加 express.json({limit:'64kb'})。上线前必做。

主要 · Major（10）

主要M-1体验 / 出题
所有选项显示为「A. A. …」：前后端各加一次字母前缀
现象后端返回的选项已含 "A. "，前端第 474 行又拼 String.fromCharCode(65+oi)。阅读理解的每个选项皆如此；完型填空的选项后端返回的是裸单词、不带前缀，不受影响。
建议后端 prompt 要求 options 只返回纯文本，字母序号交给前端统一生成。
主要M-2逻辑 / 出题

建议提交前校验是否全部作答，未完成则提示并高亮未答题号。
主要M-3体验 / 写作

主要M-4逻辑 / 写作
已提交作文以"未完成草稿"复活，可能白烧每日额度
现象submitWriting() 成功后未清 localStorage.writingDraft。刷新后提示"已恢复草稿"，编辑器为刚批改过那篇。免费版每天 3 次，用户很可能再点一次提交。
建议成功分支加 removeItem('writingDraft')。另：loadDraft() 读的是拼错的 'writingEraft'，靠 || 兜住才未出事。
主要M-5体验 / 移动
手机上仪表盘横向滑动：而它是打开的第一屏
证据
390px 视口：仅仪表盘 scrollWidth = 821px
"高频错词 TOP5" 卡释义用 truncate(nowrap)，min-content 撑到 805px
给 grid 子项加 min-width:0 → 821 → 390　溢出消失
建议grid lg:grid-cols-2 的两个直接子 div 加 min-w-0。一处解决。
主要M-6体验 / 错词
错词卡隐形删除按钮，触屏可误删且无确认
现象按钮 opacity-0 group-hover:opacity-100，但实测 pointer-events:auto、可被点中；手机无 hover，等于每卡右上压着一个看不见却能点的删除热区，deleteWord() 无 confirm。
建议触屏常显按钮（@media (hover:none)）或改左滑；删除前给确认或可撤销提示。
主要M-7逻辑 / 统计
仅 1 篇作文时进步曲线是空白框
现象模板 v-if="recentWritings?.length"（≥1 渲染）与计算 if(len<2) return []（<2 返回空）条件不一致，新用户看到只有轴标签的空盒子。
建议模板条件改 >=2；或单点时画圆点加分数标注。
主要M-8安全 / 账号
登录接口无任何限流
证据
连续 8 次错误密码 → 401 ×8，无退避 / 锁定 / 验证码
影响测试账号密码为 22（两位数字），字典可秒破。
建议按 IP + 邮箱失败计数（express-rate-limit），5 次后指数退避。
主要M-9体验 / 全站
"静默 return"通病：按钮点了没有任何反馈
现象addWord / submitFeedback / submitWriting 皆为 if(!x.trim())return，无 toast、无标红。用户只得到"点了没反应"，体感等同网站坏了。
建议用现成 showToast()，或把按钮 :disabled 与校验绑定。
主要M-10安全 / 供应链
前端依赖未锁版本、无 SRI、无 CSP
证据
unpkg.com/vue@3/...  cdn.tailwindcss.com   ← 浮动版本
Netlify 响应头无 CSP，两个 script 均无 integrity
影响token 存 localStorage；unpkg 或 Tailwind CDN 一旦被投毒，注入脚本可读走所有用户凭证。
建议锁具体版本 + integrity；进一步把 Tailwind 换构建产物、Vue 本地打包；netlify.toml 加 CSP 头。

次要 · Minor（5）

次要m-1功能 / 听写
「听写」无声，实为默写
证据全文 speakWord() 只在第 323 行（错词本卡片的"朗读"按钮）被调用；听写模板（330–400 行）没有任何 speak/audio 调用，startDictation() 里也没有，题号切换也不触发播音；模板直接把 dictationWords[dictationIndex].word 当文字渲染。
说明所以听写里连手动"朗读"按钮都没有，更没有自动播，是纯"看词写义"。错词本已有 Web Speech 朗读能力可复用。真正听写应藏词、自动播读、让学生拼写。
次要m-2功能 / 错词
错词本可存中文 / 乱码 / HTML 标签
说明你好世界、zzqwxyfoo、<img src=x onerror=alert(1)> 均入库，无 maxlength。不会 XSS（数据走插值转义），但为脏数据、会污染 AI 出题。建议限制 /^[a-zA-Z][a-zA-Z\-' ]{0,48}$/。
次要m-3完整性 / 账号
账号找回体系整体缺失
证据/auth/forgot、reset-password、verify-email、change-password 全 404。忘密码即永久锁死，无法改密码。加上注册可能是假邮箱，连"发重置邮件"都走不通。
次要m-4功能 / 后端
有删作文接口却无前端入口；后端原始错误透传浏览器
说明DELETE /api/writings/:id 通（返回 200）但写作历史无入口；写砸的作文只能永久留着拉低平均分。另 console 暴露完整 PGRST205 / public.ExerciseRecord，生产环境应做错误映射。
次要m-5安全 / 接口
CORS 完全开放
说明Access-Control-Allow-Origin: *。因用 Bearer token 非 Cookie，浏览器不自动带凭证，不构成 CSRF，风险不高；但任何站点可直接调 API，收紧到 Netlify 域名零成本。
06

做得好的

Strengths

这一节分两组。第一组是你自己做的判断，这些 AI 替不了。第二组是实测下来站得住的部分，不管代码是谁写的，结果是对的。批改的文字写得好不好，不算你的，那是模型的事。

A · 属于你的判断

✓

这是你自己的想法，不是任务

没人布置，也没有截止日期，你自己把一个想法做成了能打开的网站。现在写代码 AI 能帮很多，但"要不要做、做什么"这一步还是得自己起头。后面挑的所有毛病，都是因为这件事值得较真。

✓

没去正面做背单词，方向可以理解

那个方向百词斩、扇贝、墨墨已经占满了，新产品很难进去，绕开是合理的。但有一点要说清楚：那些产品的错词本是有来路的，先测你，你错了，那个词才进错词本。你这里是让用户自己往里输错词，这一步是反的，学习者不会这么干。方向对，起点的逻辑不对，§07 会展开。

✓

用用户自己的错词去出题，这个连接是好的

我加了五个词，生成的阅读文章把五个词都自然地放进了一个故事里，其中一道题就是考那个词。文章写得顺是模型的功劳，"拿我的数据出我的题"这个想法是你的。它成立的前提是错词得由系统替用户攒出来，现在这个前提还不成立。

✓

批改要输出什么，是你定的

分四个维度打分、统计错误类型、逐句对照修改、再给优点和建议。要哪些东西、按什么维度评，这是你的产品定义；每一格填得好不好，是模型的事。实测下来这套结构信息量很足。

✓

写作页看得出是考过试的人在设计

题库按高考、四级、六级分级，再按议论文、应用文、记叙文、图表作文分类，一共 12 篇；有考试计时、实时词数、草稿自动保存；句型库 20 条按开头、转折、论证、结尾归类。这些细节跟代码没关系。

✓

把整条链路跑通并上了线

前端、后端、大模型、鉴权、额度、部署，就算每一块都有 AI 帮忙，把它们接起来、发上线、让别人能打开，也是实打实做完了一件事。很多人做到本地能跑就停了。

B · 实测下来站得住的

✓

鉴权和越权都守住了

我用普通账号的 token 打管理接口，全是 403；用 B 账号去读、删 A 的作文和错词，全是 404，A 的数据没动；伪造一个 alg:none 的 JWT，返回 401；额度也是服务端在数。值得想一想它是怎么做到的，能不能把同样的做法用到别处。

✓

登录态失效处理得干净

把 token 换成假的再刷新，页面清掉凭证、回到登录页，没有白屏，也没卡在半登录的状态。

07

商业价值 · 完整性 · 需求现实

Business & Demand

会有人用吗：需求与获客现实

直说：按现在这个样子放出去，基本不会有人一直用。问题不在代码，在三个产品层面的决定，目前都还没做。

一、渠道不对。用的人是国内学生，可产品跑在 netlify.app 上、用邮箱登录。学生不怎么用邮箱，他们在微信小程序、App Store 和抖音里。网页也没法推送，也不会留在手机桌面上。东西再好，放错了地方等于没发。

二、错词的来路反了，这是最要紧的一条。§01 的图 4 已经画清楚了：错词本的唯一来源是用户手打，代码里没有任何一条把错误写回错词本的边。百词斩、扇贝是先测你、你错了才进错词本，用户什么都不用填；这里要用户先在别处知道自己错了，再来这里录一遍，没人会这么做。我新注册一个号进去，每一页都是空的。起点没有来源，闭环转不起来。

三、没有让人回来的机制。学习类产品靠习惯：打卡、推送、每日计划、排行榜。现在只有一个连续天数，没有通知，没有小程序，没有每日计划。就算有人来了也留不住。

不过里面有一个真能用的东西。作文批改这块质量是好的，"便宜的、能逐句改的作文批改"是有人在找的。我要是你，就做四件事：

① 只留作文批改这一个功能；② 只服务一类人，比如四六级、考研，或者高中生；③ 改成微信小程序，作文拍照上传；④ 最关键的一步，让错词本自己长出来：批改的时候模型已经把错误都找出来了，直接写进错词本；听写和出题里答错的词也自动进去。再往前一步，加一个能产生错词的正向环节，比如先测一遍词，或者拍照上传错题，让错词本像扇贝那样是测出来的结果，不是让用户自己填的。这一步做了，起点才有来源，闭环才真的转起来。

现在它更像一个演示版，截图好看，真用的时候很多页面是空的。离"有人用"差的不是十个功能，是三四个决定：渠道、给错词一个来路、批改结果自动回流。

切入点选对了：但价值还没兑现

没去碰背单词这个红海，选了错词、出题、写作、批改、回流这条线，判断是对的。错词本是攒在用户这里的数据，用得越久越不想走，前提是这些错词得是系统替他攒的、不是他自己填的；AI 批改是真能收钱的点，人工改一篇要 5 到 20 块，AI 只要几分钱；出题把这两头连上了，别人不好抄。可惜整套定价页被源码里一个 v-if="false &&" 关掉了，导航里也没有入口，用户根本到不了。触发额度上限的时候只弹一个"联系管理员"。也就是说，现在没有自助付费。

完整性 · 对齐"能收费的商业产品"必备功能

层覆盖度缺口
核心学习闭环~75%听写残缺、练习历史缺失、额度不显示
商业化闭环~10%定价页关闭、无自助支付、无订单/发票/到期提醒

完整性给 38 分的理由：当技术演示看，核心闭环有七八成了，不错。但当成一个能向国内用户收费的产品看，必备的东西只有四成不到。支付、合规、分发这三层几乎是空的，其中合规这一层不做就不能上线。好在这一层八成是流程和手续：备案、协议、支付签约、小程序审核，不是写代码。

08

这个项目真正考验的是什么

What's Being Tested

现在 AI 能把东西做出来，所以考验的重点换了。一个用 AI 做的 app，真正考的是下面四件 AI 帮不上忙的事：

能力为什么 AI 帮不上
① 判断力做什么，不做什么。你让 AI 做什么它就做什么，不会告诉你这个功能没人要。把功能砍到只剩一个，这种减法反而更难。
② 需求辨真伪AI 只会优化你给它的方案，判断不了有没有人要。"听起来合理"和"真有人每天用"是两回事，只能靠人分辨。
③ 整合与把关AI 是一块一块生成的，块与块之间的接缝没人管。这份报告里的问题差不多全在接缝上。肯不肯不信任代码、自己把整条路走一遍、测一测集成，现在比会不会写更要紧。
④ 完成度AI 很快能把你带到八成，剩下两成是空状态、错误处理、找回密码、合规、分发这些没意思的活，它不会催你做，但产品是在这两成里成型的。

以前看你会不会写。现在看你知不知道该写什么、拼出来的整体对不对、没人要的东西肯不肯停。做出来这一步你已经做到了，接下来练的是判断、整合、验证和收尾。这不是在批评，这几样现在最值钱。
